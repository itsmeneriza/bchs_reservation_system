BCHS RESERVATION FORECASTING GUIDE
=================================

Purpose
-------
This guide is for a later forecasting phase. It describes how to decide whether
the Supabase reservations data is reliable enough for a seasonal x trend
forecast, with a 4-week moving average as a fallback or comparison.

Current data source
-------------------
Reservation records are stored in public.reservations. The relevant fields are:

  reservation_code  Stable reservation identifier
  facility_id       Facility being reserved
  date              Reservation/event date
  start_time        Reservation start
  end_time          Reservation end
  status            Current reservation status
  source            staff, guest, or walk_in
  request_data      Additional reservation attributes
  submitted_at      When the reservation request was submitted

The server already reads approved and accepted rows from Supabase in
routes/forecast.js and passes them to scripts/ForecastService.js.

Planned CSV sources and provenance
----------------------------------
The existing manual-system CSVs have different reliability:

  Events   Authentic data.
  Guests   Synthetic data.
  Staff    A mix of authentic and synthetic data.

Do not combine these files as if every row were observed reservation demand.
Synthetic guest rows must be excluded from forecast training and backtesting.
For the mixed staff file, include only rows that can be independently
identified as authentic; if authenticity cannot be established for an
individual row, exclude it from the real-data series. Keep excluded rows
available in staging so they are not mistaken for deleted or missing data.

An authentic Events row is not automatically a facility reservation. Confirm
that it represents an actual facility booking/usage observation and matches
the selected forecast target. School calendar events, announcements, and
events that did not consume a facility should not be counted as reservations.

Recommended CSV integration process:
1. Preserve the original CSV files unchanged and record their filenames,
   import date, and source-system description.
2. Load each file into a staging table or temporary import process, not
   directly into public.reservations. These files may have different schemas,
   provenance, and meanings from live reservation rows.
3. Normalize facility identifiers, dates, times, status, and source fields.
   Map each candidate row to a stable source record ID so retries do not create
   duplicate observations.
4. Add explicit provenance metadata to the staging/import output, such as
   source_file, source_record_id, authenticity (authentic/synthetic/unknown),
   and import_batch. Do not infer authenticity only from the file's label when
   a file is known to contain mixed records.
5. Validate row counts, required fields, date ranges, facility mapping,
   duplicates, and representative records against the source system. Report
   excluded, invalid, synthetic, unknown, and accepted counts separately.
6. Build the forecasting weekly series from verified authentic observations.
   Avoid inserting synthetic rows into the operational reservations table.
   If historical rows must be preserved in Supabase, keep them in a separate
   historical/staging table or explicitly mark their origin and filter them
   out of live workflows.
7. Keep import batches reproducible and idempotent; never overwrite current
   reservations without an explicit matching and reconciliation plan.

Important limitation in the current implementation:
routes/forecast.js currently loads only the last completed year (and one earlier
year when available), while ForecastService.js calculates recent 4- and 8-week
trend windows relative to today's date. Those recent windows are outside the
loaded historical range, so the trend can be neutral and the moving-average
fallback can see no recent records. Before relying on the displayed prediction,
load a continuous date range that includes both the seasonal history and the
most recent complete weeks.

Is the Supabase data suitable?
------------------------------
Do not assume the data is forecast-ready merely because it is in Supabase.
Evaluate the following for each facility:

1. Provenance: Are records authentic observations? Exclude synthetic guest
   rows and unverified mixed-source staff rows from the actual forecast series.
2. Coverage: How many complete weeks and years have records? Seasonal
   comparisons should ideally have at least 2 complete years; 3 or more is
   preferable. With less history, use the moving average and label confidence
   low.
3. Completeness: Confirm that date, facility_id, start_time, and end_time are
   present and valid. Check that facilities have not changed IDs or names.
4. Consistent meaning: Decide whether the target is requests submitted,
   approved bookings, or bookings actually used. Do not mix these measures.
   For facility demand/use, count approved/accepted/completed reservations
   according to the agreed business definition. Exclude rejected, cancelled,
   refused, and blocked rows. Exclude school events or administrative blocks
   unless they are explicitly part of the forecast target.
5. Zero weeks: Build a complete weekly calendar for the observation window.
   A week with no reservations is a real zero, not a missing value. Missing
   source data or an outage must not be turned into zero-demand weeks.
6. Duplicates and corrections: Ensure reservation_code is unique and define
   how edits, cancellations, reschedules, and repeated bookings are counted.
7. Enough recent observations: The moving-average method requires four
   complete recent weeks; trend comparison requires eight. Do not use the
   current partial week as a complete week.
8. Known disruptions: Flag closures, holidays, policy changes, and other
   exceptional periods; explain how they are handled instead of letting them
   silently distort the forecast.

Recommended weekly series
-------------------------
Create a separate weekly count for each facility. Use the reservation's date
as the booked/usage date, not submitted_at. Use ISO weeks consistently, with
Monday as the first day of the week. Group by facility_id and ISO year-week.
Represent all complete weeks in the selected date range, including valid
zero-reservation weeks.

Keep aggregation server-side or query bounded date ranges from the server.
Continue using the server's service-role client; never expose the Supabase
service-role key in browser code. For large histories, paginate Supabase
queries or aggregate in the database rather than loading an unbounded table
into the browser.

Recommended formulas
--------------------
Choose one forecast target per facility (for example, number of approved
reservations per week). Let:

  Y[w]       = observed reservation count in complete week w
  base       = mean(Y[w]) across valid complete historical weeks
  seasonal   = mean for the matching ISO week across prior years / base
  trend      = mean of the latest 4 complete weeks /
               mean of the 4 complete weeks before those

Seasonal x trend forecast:

  forecast = base x seasonal x trend

If there is no usable matching-week history, insufficient coverage, or the
seasonal estimate is unstable, use the simple 4-week moving average:

  4-week MA = (Y[w-1] + Y[w-2] + Y[w-3] + Y[w-4]) / 4

Guard against dividing by zero when calculating seasonal or trend ratios.
When the comparison period is zero, do not generate an infinite factor; use a
documented neutral factor or fall back to the moving average. Apply any cap or
floor to extreme trend factors only after documenting and validating it.
Round the final reservation count to a non-negative whole number for display,
but retain the unrounded value for evaluation.

Moving average terminology matters
----------------------------------
The current ForecastService.js fallback is a 4-week WEIGHTED moving average,
not a simple moving average:

  WMA = 0.40 x Y[w-1] + 0.30 x Y[w-2] +
        0.20 x Y[w-3] + 0.10 x Y[w-4]

The weights give more influence to the most recent week. If the next phase
requires the simple 4-week moving average formula above, change the code and
label the method accordingly. Do not describe the weighted formula as a
simple moving average.

The existing seasonal method in ForecastService.js also differs from a
multiplicative seasonal x trend formula. It averages matching ISO-week counts
and applies a blended factor:

  seasonal baseline x (0.60 + 0.40 x trend factor)

It compares recent and preceding four-week reservation totals, clamps that
factor to 0.5 through 2.0, and uses the weighted moving average when there is
no matching-week history. Treat this as the current implementation, not as the
recommended formula above.

Validation before release
-------------------------
1. Confirm the weekly data window includes several years of seasonality and the
   latest eight complete weeks.
2. Compare forecasts with actual counts using time-based backtests: train on
   earlier weeks, forecast future weeks, and repeat over multiple test points.
   Never randomly split dated observations.
3. Compare seasonal x trend against the 4-week MA and a simple historical
   average. Report an error metric such as MAE (mean absolute error) by
   facility, plus the number of evaluated weeks.
4. Inspect errors by facility and season. A single overall score can hide a
   poor forecast for a smaller facility.
5. Publish the method, period, last data refresh time, coverage, and confidence
   with each forecast. Avoid high confidence when history is short or incomplete.
6. Confirm that Supabase/API errors are shown as errors. Do not turn failed
   queries into empty data or a zero forecast.

Suggested next-phase sequence
-----------------------------
1. Obtain and preserve the CSVs; profile their schemas and provenance.
2. Stage the CSV rows and separate authentic Events, synthetic Guests, and
   authentic versus synthetic/unknown Staff records.
3. Audit reservation coverage and status meaning in Supabase.
4. Implement a complete facility/week aggregation, including valid zero weeks.
5. Correct the date range so both seasonal history and recent weeks are loaded.
6. Implement seasonal x trend and the chosen 4-week average method.
7. Backtest both methods against authentic historical data and document results.
8. Enable the new forecast in the UI only after the data and accuracy checks pass.

Facility-user forecast screen: implementation instructions
==========================================================

Goal
----
Add a facility-user forecast screen based on the supplied reference:

  1. A weekly seasonal-trend chart for the selected facility.
  2. A short explanation and recommendation below the chart.
  3. A weekday-by-hour forecast grid with Low, Moderate, and Busy indicators.

This is a demand forecast, not a live availability checker. A Low indicator
must never be described as a guarantee that a reservation will be approved or
that a time slot is available. Users must still check the reservation calendar.

Current code and important limitation
--------------------------------------
The facility-user page already has a "Booking Forecast" tab. Its component
currently re-exports scripts/ForecastTab.js, which is also used by the admin
page. Do not redesign scripts/ForecastTab.js for this feature: that would
change the admin screen as well.

The existing GET /api/forecast endpoint returns aggregated analytics for all
facilities. It does not return a selected-facility weekly series or an hourly
forecast grid. Its current reservation query also omits recent completed
weeks, as described earlier in this guide. The UI code below therefore
requires a new, validated facility-specific API response before it can display
real predictions. Do not make the UI generate forecasts from arbitrary
browser-loaded records or fill missing API results with zeroes.

----------------------

  routes/facility-forecast.js

    server's service-role client, validate the facility ID, and return the

    buckets from verified reservation records. Surface query errors as HTTP
    errors; never return an empty forecast when the query failed.

  user/src/components/FacilityForecastComponent.js
    Facility-user-only renderer. The complete starter component is below.

  user/src/styles/facility-forecast.css
    Facility-user-only styles. The complete starter stylesheet is below.

  user/src/components/ForecastComponent.js
    Re-export FacilityForecastComponent as Forecast. This wrapper is already
    imported by user/src/app.js, so the app's existing tab loader and render
    call can remain unchanged. The admin continues to use scripts/ForecastTab.js.

  user/public/reservation.html
    Load /src/styles/facility-forecast.css after forecast.css.

Implement and test the server endpoint before enabling this component.

Required endpoint contract
--------------------------
Request:

  GET /api/forecast/facilities/:facilityId

Success response (HTTP 200):

  {
    "forecast": {
      "facility": { "id": "gym", "name": "Gym" },
      "targetWeek": {
        "label": "Nov 8 - 14",
        "startDate": "YYYY-MM-DD",
        "endDate": "YYYY-MM-DD"
      },
      "seasonal": {
        "title": "Quarterly usage forecast",
        "values": [
          { "label": "W1", "count": 4, "kind": "observed" },
          { "label": "W2", "count": 6, "kind": "observed" },
          { "label": "W3", "count": 5, "kind": "predicted" }
        ]
      },
      "analysis": {
        "level": "moderate",
        "message": "Demand is close to the recent average.",
        "recommendation": "Check the calendar for open times before submitting."
      },
      "hourly": [
        {
          "day": "MON",
          "date": "YYYY-MM-DD",
          "slots": [
            { "time": "8:00 AM", "level": "low" },
            { "time": "9:00 AM", "level": "moderate" },
            { "time": "10:00 AM", "level": "busy" }
          ]
        }
      ],
      "dataQuality": {
        "confidence": "low",
        "completeWeeks": 8,
        "yearsIncluded": [2024, 2025]
      },
      "lastUpdated": "ISO-8601 timestamp"
    }
  }

Use the same level values (low, moderate, busy) for analysis.level and
hourly[].slots[].level. Include the actual operating days and time slots for
the facility; the three rows above are only an example. Keep dataQuality
consistent with the validated source coverage. When there is insufficient or
unreliable data, the API should return an explicit unavailable/error response
or mark confidence low and explain the limitation; it must not fabricate a
confident estimate.

Insert: user/src/components/FacilityForecastComponent.js
--------------------------------------------------------
Replace the contents of this file with:

  import { state } from "../core/state.js";

  const escapeHtml = (value) =>
    String(value ?? "").replace(/[&<>"']/g, (character) => {
      const entities = {
        "&": "&amp;",
        "<": "&lt;",
        ">": "&gt;",
        '"': "&quot;",
        "'": "&#39;",
      };
      return entities[character];
    });

  const validLevels = new Set(["low", "moderate", "busy"]);

  export class FacilityForecast {
    constructor(container = "forecast-container") {
      this.container =
        typeof container === "string"
          ? document.getElementById(container)
          : container;
    }

    async render() {
      if (!this.container) {
        throw new Error("Facility forecast container was not found.");
      }

      const facility = state.selectedFacility;
      if (!facility?.id) {
        this.container.innerHTML =
          '<p class="fu-forecast-message">Select a facility to view its forecast.</p>';
        return;
      }

      this.container.innerHTML =
        '<p class="fu-forecast-message" role="status">Loading facility forecast...</p>';

      try {
        const response = await fetch(
          `/api/forecast/facilities/${encodeURIComponent(facility.id)}`,
        );
        const payload = await response.json();
        if (!response.ok) {
          throw new Error(
            payload.message || `Forecast API returned ${response.status}.`,
          );
        }
        if (!payload.forecast) {
          throw new Error("Forecast API response did not include forecast data.");
        }
        this.renderForecast(payload.forecast);
      } catch (error) {
        console.error("Could not load facility forecast:", error);
        this.container.innerHTML = `
          <section class="fu-forecast-message fu-forecast-error" role="alert">
            <h2>Forecast unavailable</h2>
            <p>${escapeHtml(error.message)}</p>
            <p>Please check the reservation calendar for current availability.</p>
          </section>
        `;
      }
    }

    renderForecast(forecast) {
      const { facility, targetWeek, seasonal, analysis, hourly, dataQuality } =
        forecast;
      if (
        !facility ||
        !targetWeek ||
        !seasonal ||
        !analysis ||
        !Array.isArray(seasonal.values) ||
        !Array.isArray(hourly) ||
        !validLevels.has(analysis.level) ||
        seasonal.values.some(
          (item) =>
            !Number.isFinite(Number(item.count)) ||
            Number(item.count) < 0 ||
            !["observed", "predicted"].includes(item.kind),
        ) ||
        hourly.some(
          (day) =>
            !Array.isArray(day.slots) ||
            day.slots.some(
              (slot) => !slot.time || !validLevels.has(slot.level),
            ),
        )
      ) {
        throw new Error("Facility forecast response has an invalid shape.");
      }

      const values = seasonal.values;
      const maxCount = Math.max(1, ...values.map((item) => Number(item.count) || 0));
      const confidence = escapeHtml(dataQuality?.confidence || "low");
      const chartBars = values
        .map((item) => {
          const count = Math.max(0, Number(item.count) || 0);
          const height = Math.max(4, (count / maxCount) * 100);
          const kind = item.kind === "predicted" ? "predicted" : "observed";
          return `
            <div class="fu-forecast-bar-group">
              <span class="fu-forecast-bar-value">${count}</span>
              <div class="fu-forecast-bar fu-forecast-bar--${kind}"
                   style="height:${height}%"
                   role="img"
                   aria-label="${escapeHtml(item.label)}: ${count} reservations, ${kind}"></div>
              <span class="fu-forecast-bar-label">${escapeHtml(item.label)}</span>
            </div>
          `;
        })
        .join("");

      const hourlyRows = hourly
        .map((day) => {
          const cells = (Array.isArray(day.slots) ? day.slots : [])
            .map((slot) => {
              const level = slot.level;
              return `
                <td>
                  <span class="fu-forecast-status fu-forecast-status--${level}"
                        aria-label="${escapeHtml(level)} demand">
                    ${escapeHtml(level)}
                  </span>
                </td>
              `;
            })
            .join("");
          return `
            <tr>
              <th scope="row">${escapeHtml(day.day)}</th>
              ${cells}
            </tr>
          `;
        })
        .join("");
      const slotHeaders = Array.isArray(hourly[0]?.slots)
        ? hourly[0].slots
            .map((slot) => `<th scope="col">${escapeHtml(slot.time)}</th>`)
            .join("")
        : "";

      this.container.innerHTML = `
        <section class="fu-forecast-section">
          <header class="fu-forecast-heading">
            <div>
              <p class="fu-forecast-eyebrow">Facility demand outlook</p>
              <h2>${escapeHtml(facility.name)}: seasonal trend</h2>
              <p>Forecast for ${escapeHtml(targetWeek.label)}</p>
            </div>
            <span class="fu-forecast-confidence">Confidence: ${confidence}</span>
          </header>
          <div class="fu-forecast-chart" role="img" aria-label="${escapeHtml(seasonal.title)}">
            <h3>${escapeHtml(seasonal.title)}</h3>
            <div class="fu-forecast-bars">${chartBars}</div>
            <div class="fu-forecast-legend">
              <span><i class="fu-forecast-legend-observed"></i>Observed</span>
              <span><i class="fu-forecast-legend-predicted"></i>Predicted</span>
            </div>
          </div>
          <aside class="fu-forecast-analysis fu-forecast-analysis--${analysis.level}">
            <h3>Analysis for ${escapeHtml(targetWeek.label)}</h3>
            <p>${escapeHtml(analysis.message)}</p>
            <p><strong>Suggestion:</strong> ${escapeHtml(analysis.recommendation)}</p>
          </aside>
        </section>
        <section class="fu-forecast-section">
          <header class="fu-forecast-heading">
            <div>
              <p class="fu-forecast-eyebrow">Short-term demand pattern</p>
              <h2>Hourly forecast: ${escapeHtml(targetWeek.label)}</h2>
            </div>
          </header>
          <div class="fu-forecast-grid-wrap">
            <table class="fu-forecast-grid">
              <thead><tr><th scope="col">Day</th>${slotHeaders}</tr></thead>
              <tbody>${hourlyRows}</tbody>
            </table>
          </div>
          <p class="fu-forecast-disclaimer">
            Demand estimates are not live availability. Confirm open dates and
            times in the reservation calendar before submitting a request.
          </p>
        </section>
      `;
    }
  }

The component rejects an invalid level or count instead of translating it to a
real demand category. The backend must validate and supply every forecast
value; this UI guard is not a substitute for data validation or a forecast
fallback.

Server-side data and release checklist
--------------------------------------
Before implementing the new API, decide and document what the grid measures:
historical demand by day/hour, predicted demand by day/hour, or actual
availability. Do not mix these meanings. The reference labels look like
predictions; the table above intentionally calls its cells demand levels.

The route must:
  - Count only verified reservation records matching the forecast target.
  - Exclude cancelled, rejected, refused, blocked, and duplicate records.
  - Include valid zero-demand weeks only when the source coverage is complete.
  - Use the facility's actual operating days and time slots.
  - Include recent complete weeks as well as historical seasonal weeks.
  - Mark low coverage or missing history as low confidence.
  - Return a non-200 response with a useful message when Supabase fails.

Release checks:
  1. Verify the endpoint response for every known facility and an unknown ID.
  2. Verify the weekly chart uses per-week values, not the current monthly
     buckets returned by GET /api/forecast.
  3. Verify hourly cells match the chosen day/time aggregation and data source.
  4. Verify a failed endpoint displays "Forecast unavailable", not a zero chart.
  5. Verify the facility-user tab updates to the selected facility.
  6. Verify the admin forecast still renders from scripts/ForecastTab.js.
  7. Verify the grid scrolls horizontally on a narrow screen and that labels
     remain readable without color alone conveying the demand level.

AI, school events, and DepEd academic-calendar handling
========================================================

Can AI be used?
---------------
Yes, but do not make a generative AI model the source of the numerical
reservation forecast. The data is currently limited, event records are not
attendance measurements, and yearly school dates can move. A language model
cannot reliably infer missing history or official DepEd dates.

Recommended responsibilities:

  Deterministic forecast service:
    Calculate weekly and hourly values from verified reservation observations,
    confirmed calendar periods, and known future schedule features. Return the
    numeric result, comparison periods, coverage, confidence, and method.

  Optional AI explanation:
    Use the existing server-side Gemini integration only to turn the already
    calculated, non-sensitive result into a short plain-language explanation.
    Give it validated values and approved calendar labels; require a structured
    response and validate it before display. If Gemini is unavailable or its
    response is invalid, show a deterministic server-written explanation.
    Never send user names, contact details, reservation purposes, or other
    personal data to the model. Never let AI invent numeric forecasts, classify
    actual availability, choose official school dates, or approve bookings.

Start without AI. Add AI-generated wording only after the deterministic
forecast has been backtested and the source data has been verified.

What the existing event data means
----------------------------------
The application's public.events table stores scheduled calendar events:
title, event_date, start_time, end_time, facility_id, description, and image.
It does not store attendance, confirmed demand, recurrence rules, or an
explicit academic-calendar category. An event appearing every year is not
proof that a facility reservation occurred every year.

Keep these separate:

  Reservation observations:
    The training target for demand, if their status and provenance confirm
    that they represent real facility bookings/usage.

  School events and published schedules:
    Known context for a target week. They may indicate a conflict, closure,
    school activity, or additional demand, but must not be counted as
    reservations unless separately verified as actual facility use.

  Actual availability:
    Determined by the reservation calendar and operational rules, not by the
    demand forecast or an AI-generated label.

For 2024-present records, audit each row and identify which are verified
facility-use observations and which are only scheduled events. Preserve source
and classification in staging. If annual recurrence is confirmed by staff,
store an explicit series identifier or recurrence classification and the
reviewer/source; do not infer recurrence from similar titles. For future
forecast features, only use events that are known as of the forecast's
calculation date. Do not leak future events into historical backtests unless
they were known at the time being simulated.

Representing DepEd academic transitions
---------------------------------------
Do not assume the academic year starts in the same month every year, and do
not equate ISO week number with academic week. DepEd calendars and transition
periods can change by school year. Record and verify each applicable BCHS
school-year calendar against the official DepEd order or other school-approved
source.

Apply the supplied 2024 transition information as dated, source-traceable
calendar facts, not as a rule to extrapolate to every year:

  School Year 2023-2024:
    End date: 2024-05-31, as stated in DepEd Order No. 003, s. 2024.

  School Year 2024-2025:
    Start date: 2024-07-29.
    End date: 2025-04-15, as updated in DepEd Order No. 009, s. 2024.

  2024 end-of-school-year vacation:
    The supplied policy summary identifies a mandatory 60-day vacation in
    the 2024 transition orders. Record the exact applicable vacation start/end
    dates and the covered personnel/learners from the official order or
    school-approved interpretation. Do not calculate a 60-day interval by
    simply subtracting the two school-year boundary dates, and do not assume
    this is a standing annual rule for later school years.

Before loading these dates into production, a school calendar owner should
check the order text and any amendments, confirm inclusive/exclusive date
semantics and local BCHS implementation, and preserve the source document
reference. These dates are provided here as planning inputs and must not be
treated as independently verified legal advice.

The three-term structure must also be versioned by school year. Apply it only
to school years for which the official DepEd/BCHS calendar establishes that
structure. Do not retrofit three terms onto SY 2023-2024 or SY 2024-2025 just
because a later school year uses three terms. For each applicable school year,
store each term's official name/number, dates, and source. A week that crosses
the end of one term and start of another is a term-boundary or transition
week, not an ordinary week assigned to one term without explanation.

Treat DepEd Baguio Division athletic meets and other division-level events as
separate, confirmed calendar context. Store their actual dates, location,
affected facilities, and any verified school scheduling constraints from the
applicable division memo or official schedule. An athletic meet can affect
facility use or school participation, but do not count it as a facility
reservation unless the source confirms that the facility was actually booked
or used. Do not infer annual dates, facility closures, or local rules from the
event title alone.

Recommended data table, separate from public.events:

  public.academic_calendar_periods
    id                 Stable row ID
    school_year        Label such as "2024-2025"
    term_number        Nullable term number (1-3) when applicable
    period_name        School year opening, regular classes, exam period,
                       term boundary, semester break, year-end break,
                       summer/EOSY break, transition, or confirmed division
                       event
    phase              Stable machine value such as opening, instruction,
                       exam, break, transition, term_boundary, or division_event
    start_date         Inclusive local school date
    end_date           Inclusive local school date
    facility_id        Nullable; set only when a specific facility is affected
    source_url         Official source or approved document reference
    source_order       DepEd order, division memo, or BCHS calendar identifier
    verified_at        When BCHS staff checked this period
    notes              Optional reviewed clarification

Use the published dates as the source of truth; do not generate this table
from an LLM. If inserting a new table is not yet possible, keep a versioned,
reviewed server-side calendar configuration with the same fields. Avoid
silently overwriting prior school years so that backtests can reproduce what
was known for each period.

For each reservation week or target day, derive features from the verified
date ranges, for example:

  academic phase (opening / instruction / exam / break / transition)
  school-year label
  days until or since a school-year boundary
  whether the week crosses a term/semester boundary
  confirmed holiday or school closure
  known event at the same facility and overlapping time

Treat transition and boundary weeks explicitly; do not split a week using a
fixed month assumption. If a week spans two phases, include the number of
days in each phase or label it as a transition week. Backtest by school year
and phase so that an apparently good overall score does not hide poor results
at openings, closures, or transitions. With only a few years of data, use
these features to select comparable periods and explain the result; do not
claim that a complex model has learned reliable annual effects.

What a chart-week click should do
---------------------------------
Make every weekly bar/point an accessible button, not a decorative div. The
initial view should identify the selected facility, the chart period, and
which weeks are observed versus predicted. Clicking a week should keep the
chart in place, highlight the selected bar, and update a details panel below
the chart (and above the hourly grid) with:

  - Exact week start/end dates and "Observed" or "Forecast" status.
  - Reservation count for an observed week; expected count and, where
    supported, a prediction range for a future week.
  - Confidence, method, and history coverage for that selected week.
  - Day/hour demand breakdown for that week.
  - The verified academic phase/school-year label and applicable boundary,
    break, holiday, or transition context.
  - Confirmed events at that facility during that week, clearly labeled as
    scheduled events and not added to reservation counts unless verified as
    actual usage.
  - A plain-language explanation and a reminder that the calendar, not the
    forecast, determines actual availability.

For a future week, display "Estimated demand" and confidence; never show a
predicted count as an observed booking total. For a past week, show observed
data only when the source coverage is confirmed complete. If history is
missing, show "Data unavailable" rather than a zero. Do not imply a reservation
is available just because forecast demand is low.

Recommended request flow:

  GET /api/forecast/facilities/:facilityId
    Returns the selected facility, chart points, default selected week, and
    metadata. Each chart point includes weekStart, weekEnd, kind (observed or
    predicted), count, confidence, and a stable week key.

  GET /api/forecast/facilities/:facilityId/weeks/:weekStart
    Returns that week's detail panel: daily/hourly breakdown, academic phase,
    verified matching event summaries, method, confidence, and coverage.
    Validate the facility and date, and return a clear 4xx/5xx error rather
    than fabricated empty details.

The client should fetch the default week after loading the chart, then fetch
details when a bar is clicked. Show a small loading state in the details panel
while preserving the chart. Ignore a late response if the user has selected a
different week since that request began. If the week-details request fails,
show an error in the panel and leave the chart visible. Do not issue a model
request for every click; the AI explanation should be generated server-side
from the same validated week summary, cached if appropriate, and remain
optional.

Example per-point and week-detail fields:

  {
    "weekStart": "YYYY-MM-DD",
    "weekEnd": "YYYY-MM-DD",
    "kind": "observed",
    "count": 8,
    "confidence": "medium",
    "detailAvailable": true
  }

  {
    "week": { "startDate": "YYYY-MM-DD", "endDate": "YYYY-MM-DD" },
    "kind": "forecast",
    "expectedReservations": 6,
    "predictionRange": { "low": 3, "high": 9 },
    "method": "seasonal-by-academic-phase",
    "confidence": "low",
    "coverage": { "completeWeeks": 8, "yearsIncluded": [2024, 2025] },
    "academicContext": {
      "schoolYear": "2025-2026",
      "phase": "transition",
      "label": "School-year transition"
    },
    "hourly": [],
    "scheduledEvents": []
  }

The prediction range is optional: only provide it if the selected method can
produce and validate a meaningful range. Do not create a range by adding an
arbitrary percentage to the forecast.

Tools to use
------------
Use the existing project stack first:

  Supabase PostgreSQL / Supabase SQL Editor
    Keep reservations, verified academic-calendar periods, and any provenance
    staging data in separate tables. Query and aggregate on the server. Use
    migrations/SQL files in the repository so schema changes are repeatable.

  Node.js + Express
    Implement the facility-specific API and deterministic calculations in
    server-side routes/services, following routes/forecast.js and
    scripts/ForecastService.js. Keep all service-role access on the server.

  Existing Gemini integration (optional, later)
    The repository already uses @google/generative-ai and a server-side chat
    route. If added, use Gemini only for concise explanations of validated
    results, with the API key kept in the server environment. Do not call
    Gemini directly from browser code or pass personal reservation data.

  Browser UI
    The current facility forecast has CSS styles available and can use
    accessible HTML buttons, a detail panel, and the existing CSS bar chart.
    A chart library is not required for click behavior. If a richer chart is
    wanted later, evaluate Chart.js only after confirming whether it is already
    installed; avoid adding a dependency just for a small weekly bar chart.

  Data profiling and backtesting
    Use SQL for source-row, date-coverage, duplicate, and status audits.
    Python with pandas in a separate analysis script/notebook is optional for
    exploring CSVs and producing reproducible backtest reports; it is not a
    runtime dependency and should not write unreviewed records to production.
    Compare against simple baselines using chronological rolling backtests,
    reporting MAE (and optionally WAPE) by facility and academic phase.

Suggested order of implementation:
  1. Audit what the 2024-present events and reservation records actually mean.
  2. Confirm the forecast target: requested bookings, approved bookings, or
     actual facility usage.
  3. Create and verify the school-year calendar periods from official sources.
  4. Build the deterministic weekly/hourly forecast and backtest it.
  5. Add the selectable chart and week-details API/panel.
  6. Only then consider Gemini-generated explanatory wording.
