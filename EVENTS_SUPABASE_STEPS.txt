BCHS RESERVATION SYSTEM
ADMIN EVENTS + SUPABASE SETUP

This guide explains the event migration in beginner-friendly steps.
The code has been connected to Supabase, but you still need to run the SQL and
import the existing events into your own Supabase project.

Important:
- Admins manage school events from the admin UI.
- Staff/facility users continue using their separate UI and login.
- Events refer to facilities by facility ID in Supabase.
- Facility-user requests are stored in the Supabase reservations table. Follow
  REQUESTS_SUPABASE_STEPS.txt to configure that connection.
- Never share or commit your service-role key or account password.

------------------------------------------------------------
1. WHAT THE APPLICATION DOES NOW
------------------------------------------------------------
The admin event form sends requests to /api/events.
The server routes those requests to public.events in Supabase.
The public events list also reads from /api/events.

The API keeps the familiar event data for the screens:
id, title, date, time, facilityId, location, description, image. Events do not
have an attendee-count field.
In the database, date and time are separate columns, and facility_id links to
public.facilities(id).

Event code is in:
- admin/js/events.js
- user/src/landing.js
- routes/events.js
- middleware/requireAdmin.js
- services/supabaseClient.js
- services/eventUtils.js
- server.js

------------------------------------------------------------
2. CHECK THE FACILITIES TABLE
------------------------------------------------------------
Before creating events, public.facilities must exist and contain these IDs:
auditorium, library, grounds, avr, gym.

If the table does not exist yet, run this in Supabase Dashboard > SQL Editor:

create table public.facilities (
  id text primary key,
  name text not null unique,
  capacity integer not null check (capacity >= 0),
  price_per_hour numeric(10, 2) not null default 0 check (price_per_hour >= 0),
  min_pax integer not null default 0 check (min_pax >= 0),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

Then add or update the facilities used by this project:

insert into public.facilities (id, name, capacity, price_per_hour, min_pax)
values
  ('auditorium', 'Auditorium', 700, 1800, 100),
  ('library', 'Library', 100, 1000, 40),
  ('grounds', 'Grounds', 180, 700, 50),
  ('avr', 'AVR', 150, 500, 30),
  ('gym', 'Gym', 300, 1000, 50)
on conflict (id) do update set
  name = excluded.name,
  capacity = excluded.capacity,
  price_per_hour = excluded.price_per_hour,
  min_pax = excluded.min_pax,
  updated_at = now();

The event form currently uses the existing facility choices. If you add a new
facility later, it must exist in Supabase and in the app's facility list before
the event form can select it.

------------------------------------------------------------
3. CREATE THE EVENTS TABLE AND RLS POLICIES
------------------------------------------------------------
Open the project file supabase/events.sql. Copy all of its SQL into
Supabase Dashboard > SQL Editor, then run it.

The SQL file:
- Creates public.events with a foreign key to public.facilities.
- Ensures the events table has no attendees column, removing it if it was
  accidentally added earlier.
- Enables RLS on events and facilities.
- Allows public visitors to read events and facility names.
- Allows only authenticated users with app_metadata.role = 'admin' to create,
  update, or delete events.
- Removes the broad example event insert policy named
  "Enable insert for authenticated users only" if it exists.

Do not use a policy with WITH CHECK (true) for event inserts. That would allow
any signed-in facility-user account to add events.

The admin event API forwards the signed-in admin access token to Supabase.
Therefore these RLS policies apply to app event writes; the application does
not use a service-role client for event CRUD.

------------------------------------------------------------
4. CHECK YOUR PRIVATE SERVER SETTINGS
------------------------------------------------------------
The project root .env file should contain these variable names:

SUPABASE_URL=https://your-project.supabase.co
SUPABASE_ANON_KEY=your-public-anon-key
SUPABASE_SERVICE_ROLE_KEY=your-private-service-role-key

Use the actual values from the same Supabase project that contains the
facilities table and admin account. The .env file is private and ignored by
Git. Do not paste the service-role key into admin HTML or browser JavaScript.

SUPABASE_SERVICE_ROLE_KEY is used only by trusted one-time administrative
scripts, including the admin-role setup and event migration scripts. It
bypasses RLS, so run those scripts only from your trusted computer.

------------------------------------------------------------
5. ASSIGN THE ADMIN ROLE
------------------------------------------------------------
The admin account must already exist in Supabase Authentication > Users.
The account needs app_metadata.role = "admin"; a valid email and password
alone are not enough.

The project includes scripts/AdminRole.js for assigning that role:
1. Check that its userId matches the account's User ID in Supabase.
2. Open PowerShell in the project folder:

   Set-Location "D:\BCHS reservation system"
   node .\scripts\AdminRole.js

3. Wait for the success message in the terminal.
4. Sign out of the admin page and sign in again to get a fresh token.

Do not share the account password, user credentials, or service-role key.

------------------------------------------------------------
6. IMPORT THE EXISTING EVENTS ONCE
------------------------------------------------------------
The current records are in data/events.json. The importer reads those records,
matches each old location name to a row in public.facilities, converts times
to the database format, and inserts the records into public.events.

After completing steps 2-5, open PowerShell in the project folder and run:

   node .\scripts\migrate-events-to-supabase.js

The script stops if it cannot find a facility or if public.events already has
rows. This prevents it from overwriting events. Run it only once after the
events table is ready. If it stops, read the terminal error and fix the stated
problem before retrying.

------------------------------------------------------------
7. START AND TEST THE APPLICATION
------------------------------------------------------------
Restart the server from the project folder:

   npm start

Open the admin page:

   http://localhost:3000/admin

Check these behaviors:
1. Sign in with the Supabase admin account.
2. Confirm existing upcoming events appear.
3. Create an event and verify it appears after saving.
4. Edit the event and confirm the change persists after reloading.
5. Delete a test event and confirm it disappears.
6. Open the public events page and confirm events still display.
7. Confirm another signed-in non-admin account cannot create, edit, or delete
   events.

The server port may differ if PORT is set in .env. Use the port printed in the
server terminal.

------------------------------------------------------------
8. HOW EVENTS BLOCK THE CALENDAR
------------------------------------------------------------
The calendar builds a temporary/synthetic reservation from each event
returned by /api/events. This blocks the facility and time slot and lets the
existing conflict checker work. The event is not duplicated as a user
reservation record.

The event API returns location as a facility name for existing screens and
facilityId as the shared facility ID. The database itself stores only
facility_id as the relationship.

------------------------------------------------------------
9. TROUBLESHOOTING
------------------------------------------------------------
"Could not load events from Supabase":
- Confirm you ran supabase/events.sql.
- Confirm public.facilities and public.events exist.
- Confirm SUPABASE_URL and SUPABASE_ANON_KEY point to the correct project.
- Check the server terminal for the Supabase error details.

"The selected facility was not found in Supabase":
- Check the event's facility exists in public.facilities.
- Ensure the facility ID is the expected ID, for example auditorium.
- Ensure the signed-in admin token can read facilities; the SQL file adds the
  public read policy.

"Administrator access is required":
- Confirm the account has app_metadata.role = "admin", not a user_metadata
  value.
- Sign out and sign back in after assigning the role.
- Confirm the server and admin account use the same Supabase project.
