BCHS RESERVATION SYSTEM
FACILITY-USER REQUESTS + SUPABASE SETUP

This guide connects facility-user reservation requests to Supabase. Follow the
steps in order. Do not put a service-role key in browser code, commit it, or
share it.

------------------------------------------------------------
1. WHAT THIS CONNECTION DOES
------------------------------------------------------------
The server now handles these reservation endpoints using public.reservations:

  POST   /api/requests       Save a facility reservation or admin walk-in
  GET    /api/requests       List requests for the app's existing screens
  GET    /api/requests/:id   Get one request by its reservation code
  PATCH  /api/requests/:id   Update a request
  DELETE /api/requests/:id   Delete a request

The table stores reservation fields in regular columns and keeps the rest of
the app's existing request fields in request_data (JSONB). This preserves
rescheduling, cancellation, visit, utility, and admin-edit details that are
not separate table columns.

Request source values:
  staff    A facility-user request submitted by a staff member
  guest    A facility-user request submitted by a guest
  walk_in  An admin-entered reservation or facility block

The user app calls the server API; it does not connect directly to the
reservations table. The server uses SUPABASE_SERVICE_ROLE_KEY, which bypasses
row-level security. Keep the server environment private and never expose this
key to the browser.

------------------------------------------------------------
2. CHECK SUPABASE PREREQUISITES
------------------------------------------------------------
The same Supabase project must already contain:

  public.facilities
  public.staffs
  public.guests

The facilities table must contain the facility IDs used by this app, including
auditorium, library, grounds, avr, and gym.

The shown staffs table uses a UUID primary key in id, and a separate text
staff_id login code (for example, STF028). The reservation's staff_id foreign
key references public.staffs(id), so it is UUID. The app sends that UUID as
staffId; the login code is not used as the foreign key.

The guests table's id is UUID as well, so reservations.guest_id is UUID and
references public.guests(id), just as reservations.staff_id is UUID and
references public.staffs(id).

Guest phone login uses public.guests.mobile_number. In Supabase SQL Editor, run
supabase/guests.sql once to add that column and ensure each mobile number maps
to at most one guest account. When a mobile number is not found, the server
creates a guest record using that number.

If you still need to create facilities or configure the event table, see
EVENTS_SUPABASE_STEPS.txt and supabase/events.sql.

------------------------------------------------------------
3. CONFIGURE PRIVATE SERVER ENVIRONMENT
------------------------------------------------------------
Create or update the project-root .env file (not .env.local) with the values
from the same Supabase project:

  SUPABASE_URL=https://your-project.supabase.co
  SUPABASE_ANON_KEY=your-public-anon-key
  SUPABASE_SERVICE_ROLE_KEY=your-private-service-role-key

The service-role key is used only by server-side code and trusted migration
scripts. Never place it in user/src, admin/, HTML, or any file sent to a
browser. The repository ignores local .env files; still verify the file is not
tracked before adding credentials.

------------------------------------------------------------
4. CREATE THE RESERVATIONS TABLE
------------------------------------------------------------
In Supabase Dashboard:

  1. Open the SQL Editor for the project.
  2. Open supabase/requests.sql in this repository.
  3. Copy the complete SQL file into the SQL Editor and run it.
  4. Confirm the query finishes successfully and public.reservations exists.

The SQL creates the reservations table, links facility/staff/guest records,
adds the source and workflow columns, creates lookup indexes, and installs an
updated_at trigger. It enables row-level security and revokes direct table
access from public, anon, and authenticated roles. The private server
service-role client performs database operations.

If SQL reports that public.staffs or public.guests does not exist, first
complete the database setup for those tables. Do not remove the foreign keys
or grant public access as a workaround.

------------------------------------------------------------
5. RESTART THE SERVER
------------------------------------------------------------
From PowerShell in the repository folder:

  Set-Location "D:\BCHS reservation system"
  npm start

Restart the server whenever .env values are changed. Confirm the terminal
prints the server's listening port without a Supabase configuration error.

------------------------------------------------------------
6. VERIFY NEW REQUESTS
------------------------------------------------------------
Use the app in a browser:

  1. Sign in as a guest or staff facility user.
  2. Submit a test reservation.
  3. Confirm the app reports that the request was submitted.
  4. In Supabase Dashboard > Table Editor > reservations, confirm a new row.
  5. Confirm source is guest or staff, and facility_id, date, times, status,
     and reservation_code match the submitted request.
  6. Reload the user app and admin page; verify the request is still visible.
  7. Update the request in the admin workflow and verify the same row changes.
  8. If testing an admin-entered reservation, confirm source is walk_in.

The reservation code is the app-facing ID. Supabase also assigns its own
numeric primary key. The API uses the reservation code in /api/requests/:id so
existing links and browser code continue to work.

------------------------------------------------------------
7. EXISTING JSON DATA
------------------------------------------------------------
Connecting the API does not automatically copy old records from
data/requests.json or data/accepted.json into Supabase. Existing JSON files
remain unchanged. The new reservations table will contain new requests only
until old records are imported separately.

Before importing existing data, make a private backup and deduplicate records
by reservation ID. Do not import school events from data/events.json as
reservations. Confirm the target table is empty or that the import process
will skip reservation codes that already exist.

------------------------------------------------------------
8. TROUBLESHOOTING
------------------------------------------------------------
"SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY must be configured."
  Check that both values are in the project-root .env file, then restart npm.

"Could not save reservation."
  Check the server terminal for the Supabase error. Verify that the table
  exists, the selected facility_id is present in public.facilities, the
  staff/guest foreign-key IDs exist, and date/time values are valid.

Supabase reports a missing staffs or guests table:
  Create or correct those user tables first. requests.sql references them to
  retain the relationship between a reservation and its facility user.

Request submission succeeds but old requests are not shown:
  Old JSON requests are not imported automatically. Follow section 7 before
  expecting historical records to appear from Supabase.

Do not solve permission errors by granting anon or public direct access to
reservations. Check that the server has the private service-role key instead.
